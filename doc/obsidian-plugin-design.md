# Augmented Awareness as an Obsidian plugin

## Recommendation and effort

A native TypeScript plugin is practical for retrospective creation. The first useful release should generate daily, weekly, monthly, and yearly retrospectives inside the open vault, using the existing note paths and prompt text. With a developer actively using an AI coding agent for code translation, tests, and iteration, this is roughly **9–14 focused working days (about 2–3 weeks)** when [AI Providers](https://github.com/pfrankov/obsidian-ai-providers) handles LM Studio, the mock server, and OpenRouter, alongside content-based cache invalidation. A daily-only proof of concept is closer to **1–2 days**, but it would leave the dependency and cache behavior unproven.

Chat is a separate **large phase**, roughly **8–15 additional focused working days (about 2–3 weeks)** for a useful chat pane with selected vault tools, sessions, and basic search. Full parity with the current Python chat tools and local semantic search could take **another 15–30 working days (about 3–6 weeks)**, depending on the search implementation. These are planning estimates, not commitments. They assume one experienced developer, a working AI-assisted development setup, a disposable Obsidian test vault, AI Providers integration in v1, existing prompts and Python tests as references, and focused time. The v1 estimate assumes model-initiated linked-page reading is deferred; adding it requires a separate tool-call loop and additional provider tests. Part-time work stretches the calendar time.

| Work in the retrospective release | Focused working days with AI assistance |
| --- | ---: |
| Capture parity fixtures and scaffold the plugin | 1–2 |
| Port date/path/input/prompt rules, dependency planning, and content fingerprints | 3–4 |
| Integrate AI Providers, add Obsidian commands/settings, progress, and safe writes | 2–3 |
| Test in Obsidian, fix edge cases, and document installation | 3–6 |
| **Total, allowing overlap** | **9–14** |

An AI coding agent should shorten the mechanical port and test authoring substantially. Reusing AI Providers removes most provider-specific HTTP and credential UI work, saving roughly 1–2 days from the earlier 10–16 day estimate. AI assistance does less to shorten decisions about cache semantics, provider behavior, and privacy, or the manual check that generated notes remain correct in a real vault. The upper end applies if those checks uncover changes needed in the existing Python behavior. The estimates exclude a public community-plugin submission and the later Go/Streamlit workflows.

The plugin can eventually become the main Obsidian interface, but “all functionality” spans more than retrospectives and chat. The repository also contains Python ask/compare/MOTD/prompt workflows, Streamlit pages, a LanceDB and sentence-transformer search stack, and Go CLI/TUI, tasks, metrics, search, and MCP commands. Port those by user workflow, not by translating each command one for one. Keep the existing tools usable during migration.

## First release: retrospective creation

### Milestones and smallest useful step

Build these in order. Each milestone leaves a runnable plugin in a disposable vault; later milestones extend the same path rather than introducing a second generation workflow. The time ranges sum to the **9–14 focused working days** above and include agent-assisted implementation and focused checks. Keep the Python generator and its test fixtures available throughout.

| Milestone | Time | Smallest self-contained result | Done when |
| --- | ---: | --- | --- |
| **1. Daily vertical slice** | 1–2 days | Install a desktop-only plugin in a test vault, configure the Python echo server in AI Providers, save its provider ID in a minimal plugin setting, and run **Generate retrospective for active note** on one daily journal. Create a missing daily target and open it; leave any existing target untouched. | A real Obsidian command produces `retrospectives/<year>/<month>/r<date>.md`; the server sees one request, and an invalid active note makes none. This also proves the SDK works with the installed AI Providers version. |
| **2. Match daily input** | 1–2 days | Port the Python daily path, frontmatter, heading-removal, code-fence, metrics, tags, and prompt-rendering rules. Add edge cases for leap day and missing journals. |
| **3. All period levels** | 2–3 days | Add week, month, and year expansion and the shared dependency graph. Generate each period through the same command from its journal note, using bounded parallel model calls. Keep existing targets untouched for now. | Python and TypeScript echo traces agree on paths, call order within dependency constraints, prompts, and input parts for representative weeks crossing New Year, months, and years. The first milestone is the smallest end-to-end proof: one command, one daily source, one model request, and one new note. It deliberately excludes recursive context, cache reuse, and replacement of existing files. If its SDK smoke test fails, resolve that integration before extending the planner; the internal `ModelAdapter` lets the echo parity work continue without binding the core to a provider API.

### Development vaults

Use `demo_vault/demo_vault` as a **read-only seed**, copied to a disposable vault for Obsidian CLI, UI, provider, cache, and migration tests. All development and test runs happen in that disposable copy — never open the plugin against the main vault, which contains the real journal. It has 83 daily journal notes across 2024–2025 and generated daily, weekly, monthly, and yearly retrospectives. Of its 625 retrospective Markdown files, 470 are numbered backups; tests should distinguish canonical targets from these historical copies. The adjacent `retrospectives-gpt4.1` and `retrospectives-gemini-2.5-pro` directories are prior model outputs for qualitative comparison, not expected text for deterministic parity.

The copied vault needs its broken `aww-retro-obsidian-plugin` symlink replaced by the new build, AI Providers installed and configured for the echo server, and Obsidian Sync disabled before opening it. Keep the source vault unchanged and reset or recreate the disposable copy between destructive test runs. For milestone 1, pick an existing daily journal and remove only its target retrospective **in the copy** to exercise creation. For regeneration and conflict tests, retain canonical retrospectives in the copy to exercise legacy-note handling. The demo has no weekly, monthly, or yearly journal notes, so add a few synthetic period notes to the copy when testing commands launched from those note types.

Keep a separate tiny, versioned fixture vault for exact Python-versus-TypeScript echo comparisons. The full demo is too large for concatenated-prompt echo output and has many pre-existing retrospectives that complicate expected call traces. Use the demo copy for realistic traversal, missing-day behavior, old metadata, numbered-backup coexistence, and performance; run a bounded date range or short-output mock before any full-year test. Real-model prose from the existing snapshots is useful to inspect by eye, but it is not a stable equality assertion.

### User flow

1. In a daily, weekly, monthly, or yearly journal note, run **Generate retrospective for active note** from the command palette or a note menu. This command uses saved defaults and opens no dialog, so the CLI and an agent can invoke it. A separate **Generate retrospective with options** command opens a dialog to choose a period, date, and overrides.
2. The options command previews the target path, selected model, context levels, reuse decisions, and estimated **request count** before generation. The no-dialog active-note command starts immediately with saved defaults and reports the same plan in a non-blocking progress view; the request count is an estimate, not a promised cost.
3. Generate with visible progress and a Cancel action. If a daily journal is absent, skip that day and report it in the result; if the selected daily note is absent, stop before making a model call.
4. Save the output as a Markdown note under `retrospectives/`, then open it. Regeneration updates the existing target note in place after a conflict check.
5. On failure, leave existing notes intact and show which nodes completed and which failed. A retry reuses completed notes where valid.

Settings: journal folder, retrospective folder, selected AI Providers provider/model, ignored daily headings, canonical tags, context levels, and concurrency. Add a follow-links toggle only if the model-initiated tool loop is included in v1. Provider URLs and credentials stay in AI Providers settings. Advanced controls can expose cache policy per run. By default, regenerate the selected root, reuse plugin-generated children by fingerprint, and use the Python modification-time rule only for legacy children without fingerprints. Include all lower levels as context. No automatic background generation in v1.

### Proposed modules

```text
obsidian-plugin/
  manifest.json, package.json, esbuild.config.mjs
  src/main.ts                 commands, settings, lifecycle
  src/ui/GenerateModal.ts     date/level/options and progress
  src/core/calendar.ts        thin wrapper over Obsidian Moment for ISO weeks and period expansion
  src/core/paths.ts           legacy-compatible journal/retro names
  src/core/plan.ts            dependency graph and cache decisions
  src/core/input.ts           Markdown cleanup and metrics; linked pages if included
  src/core/prompts.ts         bundled prompt assets and rendering
  src/core/generate.ts        bounded DAG executor and cancellation
  src/core/output.ts          Markdown and YAML metadata
  src/adapters/VaultStore.ts  interface backed by Obsidian Vault
  src/adapters/Model.ts       interface and AI Providers SDK adapter
  tests/                     fixture-based parity tests
```

The core modules should not import Obsidian except for `calendar.ts`, which imports Obsidian's bundled `moment`; tests can mock that one import with the Moment package. `VaultStore` exposes read, existence, metadata, create-folder, create, and modify operations; its Obsidian implementation uses `TFile` and `app.vault`. The model interface returns text, selected provider/model identity, token usage when available, and a structured error. The AI Providers SDK currently documents `execute()` as returning text, so token counts may be unavailable; omit those YAML fields rather than inventing values. This keeps provider changes and later chat independent of date/path logic. Obsidian's [Vault API](https://docs.obsidian.md/Plugins/Vault) supports reading and writing vault files.

### Calendar library: use Obsidian Moment

The installed [Natural Language Dates](https://community.obsidian.md/plugins/nldates-obsidian) plugin uses Chrono to parse phrases such as “next Friday,” then exposes a Moment result through its `parseDate()` API. That parsing solves a different problem from retrospective planning: the first release starts from a journal filename or a date picker, and must expand exact calendar days, months, years, and Monday–Sunday ISO weeks. Do not require Natural Language Dates for those rules. Its API could be an optional input convenience later if the options dialog accepts free-text dates.

Use [`moment` exported by Obsidian](https://docs.obsidian.md/Reference/TypeScript%2BAPI/moment), rather than bundling another copy. Keep `calendar.ts` small: strict parsing of `YYYY-MM-DD` and journal period names, `startOf('isoWeek')`, `isoWeek()` and `isoWeekYear()`, `daysInMonth()`, and calendar-day iteration. Moment's [ISO week tokens and operations](https://momentjs.com/docs/) cover the Python `date.isocalendar()` behavior; use the ISO week-year for `yyyy-Www` filenames, which can differ from the calendar year near New Year. Clone Moment values before `startOf` or `add` because those methods mutate their input. Compare its outputs against Python fixtures across year boundaries, leap days, and daylight-saving transitions. This reuses Obsidian's existing date library while keeping path rules and dependency expansion in our own code.

### Provider boundary: decision 1

Use [AI Providers](https://github.com/pfrankov/obsidian-ai-providers) as the v1 provider backend. Version 1.10.0 is installed and working alongside Local GPT in an existing vault, which de-risks the integration. Its [published SDK](https://github.com/pfrankov/obsidian-ai-providers/blob/master/packages/sdk/README.md) exposes configured providers and `execute()` with system/user messages, streaming progress, cancellation, and model selection. At runtime the service is not an import: the plugin assigns it to the `app.aiProviders` global and fires an `ai-providers-ready` workspace event; consumers read the global (or wait for the event) and call `checkCompatibility()` — the installed service reports version 4 (verified against the installed 1.10.0 bundle and Local GPT's usage). The bundle's handler map covers openai, openrouter, ollama, gemini, lmstudio, anthropic, groq, mistral, together, fireworks, perplexity, deepseek, xai, and more, including custom OpenAI-compatible endpoints. AI Providers configuration is per-vault (`data.json`), so each disposable test-vault copy needs its own provider entries: the echo server first, LM Studio for the live local check, and OpenRouter — supported but not yet configured anywhere — added for milestone 6's manual check. LM Studio itself is a machine-level service at `localhost:1234` reachable from any vault, and OpenAI and Gemini are proven working through AI Providers. The installed bundle also contains `toolsExecute()` (which the SDK documents for later chat tool calls) and `embed()`/`embedForce()`, which matter for the phase-4 search spike. Pin a compatible SDK version and verify the installed plugin's service API with a small runtime smoke test before implementing generation.

Keep a small internal `ModelAdapter` contract so the planner and prompt tests do not depend on the SDK. The production adapter obtains the current AI Providers service when making a request, selects the saved provider/model, and sends explicit system and user messages. Avoid storing a stale service instance across provider changes. In v1, treat AI Providers as an installed-and-enabled dependency and show a clear setup message if it is unavailable. Store the selected provider ID in our settings; credentials and endpoint configuration remain in AI Providers. An alternate direct HTTP adapter can be added later only if a required feature is missing.

Configure the Python echo server as a custom OpenAI-compatible provider in AI Providers. It should return concatenated prompt and input and record received requests; the plugin should separately record its logical messages before calling the SDK. This tests prompt/input parity even when AI Providers transforms the wire request. Use LM Studio for a live local check and OpenRouter for a manual remote check. Provider behavior still needs integration tests: `execute()` returns text without documented token-usage metadata, and OpenRouter reasoning chunks may appear in the text as `<think>...</think>`. Strip or reject such reasoning wrappers before writing a retrospective, with a fixture test. Do not put secrets or raw journal text in routine logs. For phase 2, test `toolsExecute()` — the installed bundle takes `{provider, messages, tools, tool_choice, abortController, onProgress}`, with tools passed top-level rather than inside options — and model capabilities with each selected provider; SDK support for tools does not guarantee that every model handles them well.

### Planning and cache rules

The planner computes all required paths before calling a model. Each node is keyed by `{level, targetPath}` so a shared daily/weekly result is generated at most once per run. Keep the Python graph and model inputs as the parity baseline. V1 retains the CLI's explicit cache controls, including “regenerate root” and “regenerate all,” while using content fingerprints by default for notes generated by the plugin.

The graph is a directed acyclic graph rather than a strict tree because nodes can be shared across periods. Treat it as a Merkle-style dependency graph: process child nodes first, then compute each node's `input_fingerprint` from the exact rendered system prompt, ordered user input parts (including the current content of child retrospectives and the same-level journal note), provider/endpoint identity, model ID, and generation settings that affect output. Use a versioned, length-prefixed UTF-8 encoding and SHA-256 so boundaries and ordering are unambiguous. Hash the effective content sent to the model, not only file modification times. Store the fingerprint and an `output_fingerprint` of the retrospective body as seen by later nodes in generated frontmatter; exclude generated metadata such as creation time from the output hash.

If an existing target has the same `input_fingerprint` and its current content matches `output_fingerprint`, reuse it without a model call or file write. If a child regenerates but produces the same content, its parent can still be reused. If a source, prompt, selected model/settings, or child output changes, only dependent ancestors need regeneration. A manual edit to a retrospective changes its output fingerprint, so its ancestors must see the edited content; do not silently overwrite that edited note. Show a conflict/review action for that target. “Regenerate root” and “regenerate all” override fingerprint reuse.

The existing Python modification-time rule compares each journal note with its same-level retrospective. It does **not** propagate a changed daily note through an existing weekly/monthly/yearly retrospective, nor detect a changed prompt or model. Preserve that rule in the Python parity fixtures and as a fallback for existing notes without plugin fingerprints. On first use of a legacy note, show whether the run will trust its legacy cache or regenerate it and establish a fingerprint. A changed lower-level output invalidates a legacy parent even if the old modification-time rule would reuse it. Do not silently treat an old note as verified by the new cache. When `follow_links` is enabled, record each page read by the model, including missing links, with its content/existence fingerprint and recheck those dependencies before reuse.

For writes, generate complete content in memory first. Recheck source and child content fingerprints immediately before saving; if an input changed while the model was running, abort or replan that node. Create missing folders and use `Vault.create()` for a new target; use `Vault.process()` for an existing target, checking the current content against what was read before generation and aborting on conflict. Serialize writes to a given target path. Keep `sources` links and existing metadata keys (`sys_prompt_hash`, `user_prompt_hash`, `model_name`, `ctime`, token fields) where available; add a plugin schema/version field. Model output should be stripped of an enclosing `` ```markdown `` fence (the Python `MARKDOWN_RE` matches only a fence wrapping the whole output), normalize `![[` embeds to `[[` as the Python code does, and receive the `# <target name>` heading.

Use Obsidian's [File recovery](https://obsidian.md/help/plugins/file-recovery) as the normal way to inspect or restore older text, and the CLI's [history/diff commands](https://obsidian.md/help/cli) during development. File recovery takes periodic snapshots (by default at least five minutes apart, retained for seven days), so it does **not** guarantee one saved version per generation. That is acceptable here: numbered backups were only for prompt experiments. For exact experiment comparison, save echo traces and generated fixtures in the development test suite or commit a disposable test vault to Git.

### Provider and privacy behavior

Use AI Providers' existing configuration for provider URLs and API keys; our plugin stores only a provider ID and optional model override. Provider requests send journal content, selected metrics, and optionally linked page content to the configured endpoint. Show this plainly next to provider selection and when enabling follow-links. Resolve `[[links]]` through Obsidian's metadata/link APIs, bound the number and size of pages per generation, and never allow the model to read arbitrary filesystem paths. The plugin should work offline only when the selected endpoint is reachable locally; local inference is still an external process and is not bundled.

This is a **desktop-only plugin**. Set `isDesktopOnly: true` in the manifest, as defined by Obsidian's [manifest reference](https://docs.obsidian.md/Reference/Manifest). No mobile UI, compatibility testing, or mobile dependency restrictions are required. Use the Obsidian Vault API for journal and retrospective files so Obsidian tracks changes; Node APIs remain available for desktop-only integration with local services where useful.

### Acceptance tests

- Make the Python generator the reference for a fixed test vault. At the model boundary, replace the real model with a deterministic **echo model** that records each call's level, target path, exact system prompt, and ordered user input parts. Its response is readable Markdown containing the full system prompt followed by the numbered input parts, with clear delimiters and no normalization. Run golden trace comparisons with concurrency set to one, then compare both the ordered trace and resulting files. A diff then shows the exact text that changed, including source order, prompt rendering, and links. Test higher concurrency separately for correct dependencies and deduplication. Do not compare timestamps or provider-specific token counts byte for byte.
- Echoed daily output becomes input to weekly generation, and so on, so full-year echo output can grow very large. Use small fixtures for end-to-end echo tests. For large-period planner tests, retain the full input in the call trace but return a short deterministic marker (for example, the target path) to keep generated files bounded. The readable trace remains the source of truth for prompt and input parity.
- Golden tests compare TypeScript path/date expansion and prepared model inputs against Python fixtures for daily, week 1/week 53, leap day, month end, year end, ignored sections, metrics, missing notes, and canonical tags.
- Planner tests cover all four periods, shared dependencies, cache choices, stale/changed targets, changed prompts/models, edited retrospectives, linked pages, and the case where a regenerated child has unchanged output so its parent is reused.
- Mock-provider tests prove bounded concurrency, cancellation, partial failures, and no duplicate model call for one node.
- In a disposable Obsidian vault, generate each period, inspect YAML and links, regenerate once, confirm the target note is updated in place, and verify a concurrent edit produces a conflict instead of being overwritten.
- After deterministic tests pass, run one small end-to-end generation against LM Studio. Require nonempty, parseable Markdown and a correctly saved note. Test OpenRouter manually with a currently available low-cost model, selected through its [models API](https://openrouter.ai/docs/api/api-reference/models/get-models). These checks cover HTTP/authentication and response handling; model prose quality is outside the parity gate. Add other providers through explicit adapter tests as needed.
- Compare real-model outputs structurally (headings, sources, metadata, input pages), not word for word: model responses can vary between calls.

### Decisions to settle before milestone 2

1. **Linked-page reading:** Python's `follow_links` lets the model invoke `read_pages` during generation. The v1 `execute()` adapter handles text only. Recommended v1 scope: leave `follow_links` off, as it is by default in Python, and add the `toolsExecute()` loop alongside chat later. If linked-page reading is essential for the first release, include the tool loop and tests for provider capability, tool-call limits, page-read limits, and fingerprinting pages actually read; revise the estimate upward.
2. **Prompt customization:** Bundled, versioned prompts give reproducible defaults, but they do not support the prompt experiments that motivated numbered backups. Recommended approach: ship bundled defaults and allow an optional vault folder containing four editable prompt files. Hash the rendered prompt in the input fingerprint, and show which prompt source a run used. The first release can omit the override if prompt editing in the source repository is sufficient during development.
3. **Legacy retrospective reuse:** Existing notes have Python metadata but no content fingerprints. Recommended no-dialog default: reuse a legacy child when its same-level journal is absent or older, regenerate the selected root, and report which legacy notes were trusted. The options command can offer “regenerate legacy dependencies” to establish fingerprints. This makes the first run predictable without requiring a modal confirmation for every old note.

### Agent development loop: Obsidian CLI and MCP

Use the [official Obsidian CLI](https://obsidian.md/help/cli) as the main bridge between an AI coding agent and a running desktop Obsidian test vault. It can target a vault explicitly, list and execute plugin commands, reload a plugin, read generated notes, inspect captured JavaScript errors/console output, and take screenshots. The current official setup requires an Obsidian 1.12.7+ installer and the CLI setting enabled; the desktop app must run. On the development machine this is already satisfied (Obsidian 1.13.7 installed and the CLI setting enabled in the Obsidian configuration); still verify that the CLI can connect to the disposable test vault before relying on it for the development loop.

The plugin should register a **Generate retrospective for active note** command with no modal requirement. That gives the agent a stable CLI path: build the TypeScript bundle, reload the plugin, open a fixture note in the disposable vault, execute the command, wait for the target note, read it, and check `dev:errors`/`dev:console`. Invalid active notes should produce a clear error without starting a model call. Give each run a completion/error status the test harness can observe, because invoking an async command does not by itself prove generation finished. Use `dev:screenshot` for visual checks and `eval` only for narrowly scoped assertions against the live Obsidian API. The CLI's generic `command id=...` invokes a registered command but does not pass arbitrary date/model arguments, so core logic still needs direct unit tests and settings/fixture-driven integration tests. Check the actual plugin command IDs with `commands filter=...`.

A native desktop UI agent would add coverage for settings, the date picker, progress and cancellation, error notices, and the generated note's appearance. Give it a separate test vault and a slow/deterministic mock-model mode so it can observe and cancel a run reliably. Obsidian CLI also exposes `dev:dom`, `dev:css`, `dev:cdp`, `dev:screenshot`, and `dev:errors`; use those for inspection before adding another browser automation layer. A conventional browser agent controls browser tabs and will not automatically see Obsidian's Electron window. Use native-app automation or an explicitly attached Electron DevTools session for live UI interaction. Keep visual/UI checks small; the Python-versus-TypeScript echo suite remains the authoritative behavior check.

Third-party MCP tools are optional for this local coding workflow. The [Local REST API plugin](https://github.com/coddingtonbear/obsidian-local-rest-api) now exposes its own MCP endpoint with live vault read/write/search and command tools, using a bearer token. A [CLI-wrapping MCP server](https://github.com/Storks/obsidian-mcp) mainly repackages the official CLI, while other [REST-backed MCP servers](https://github.com/cyanheads/obsidian-mcp-server) add structured note edits and permission controls. These are useful when an agent client has MCP access but no shell, or when structured note operations are needed. They add installation, credentials, and another failure point; they do not replace the CLI's plugin reload and developer diagnostics or the Python-versus-TypeScript parity suite. If used, connect them only to a disposable test vault and limit write access to that vault.

For phase 2, store new plugin chat sessions as versioned JSON in plugin data or vault Markdown, with an export path. Existing Python sessions use SQLite and Pydantic AI message serialization, so importing them needs an explicit converter and tests; they are not directly reusable. Start search with Obsidian's metadata and text search capabilities. Full parity with `aww/rag.py` means replacing or bridging LanceDB, sentence-transformer embeddings (`all-mpnet-base-v2`), and cross-encoder reranking (`ms-marco-TinyBERT-L-6`); that remains a distinct technical spike. A local Python sidecar could reuse the existing search stack, while a pure TypeScript port would require a new embedding and index implementation. A middle path exists for embeddings: the AI Providers service exposes `embed()`, and an LM Studio embedding endpoint (nomic-embed-text) already runs locally and is proven with AI Providers — the development vault just needs its own provider entry — though cross-encoder reranking would still need a sidecar or a TypeScript replacement.

Chat write tools should show the proposed file and diff before applying it. `python_eval_tool` should be replaced with a small calculator/date tool, not a JavaScript evaluator. Constrain page reads and skill loading to the vault. The first chat release can omit writes and semantic search while still providing useful conversations over selected notes and period summaries.

The design assumes existing journal and retrospective names are authoritative, users configure a provider credential, and retrospective generation is started explicitly. These assumptions can be changed without rewriting the core date and dependency logic.
